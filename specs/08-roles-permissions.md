# Роли и пермишены

## Принципы

1. **Пермишен — атомарное действие** с стабильным кодом (`users.create.student`).
   Код никогда не переименовывается «молча»: меняется значение, код остаётся.
2. **Роль — именованный набор пермишенов.** Базовые роли заданы системой
   (admin / teacher / student); в пост-MVP — собственные роли платформы
   (`roles.yml` = роль → набор кодов), для этого каталог кодов уже резервируется.
3. **Deny by default.** Всё, что не выдано ролью, запрещено.
4. **Роль даёт способность, контекст сужает область.** Пермишен
   `courses.manage` у учителя действует только на *свои* курсы; проверка
   области (ownership/membership) — отдельный шаг контекстной проверки.
5. **Одна точка проверки.** Весь код спрашивает `can(actor, code, context)` из
   центрального модуля; разбросанные проверки (`requireRole`, локальные
   `canManage` в адаптерах) выносятся туда же при рефакторинге шага 3.
6. **Приватность не ослабляется пермишенами:** даже «просмотр списка»
   отдаёт только псевдонимы; список аккаунтов *платформы* — только админ.

## Роли

| Роль | Описание |
|---|---|
| `admin` | Администратор платформы: все пермишены, включая управление аккаунтами |
| `teacher` | Учитель: создаёт курсы и учеников; полные права на **свои** курсы |
| `student` | Ученик: чтение и участие **в зачисленных** курсах |

Супер-правило owner-скоупа: для учителя все ресурсные пермишены
(`courses.*`, `materials.*`, `assignments.*`, `submissions.*`, `schedule.*`)
действуют только на курсы, где он `teacher` этого курса; для админа — на любые.

## Механика проверки

```ts
// server/lib/permissions.ts — чистая карта роль → пермишены (без IO)
export interface PermissionContext {
  courseSlug?: string        // ресурсная область, если применимо
}

export function can(actor: UserPublic, code: string, ctx?: PermissionContext): boolean
```

Два уровня проверки:

1. **Способность** (`can` по карте ролей) — быстро, без IO.
2. **Область** (контекст) — при наличии `courseSlug` проверяется
   владение/зачисление через `ContentStore`; эта часть живёт в
   `server/utils/can.ts` (обёртка с IO) и кэшируется в рамках запроса.

Валидация кодов пермишенов — статическим типом (union), опечатки ловятся на
компиляции, а не в рантайме.

## План внедрения

1. **Шаг 3 (материалы):** вводится модуль `permissions.ts` + `can()`;
   существующие проверки (`requireRole`, `canSee`/`canManage` в адаптерах)
   переводятся на него — это рефакторинг без изменения поведения.
2. **Шаги 4–5:** новые роуты пишутся сразу через `can()`.
3. **Пост-MVP:** собственные роли (`users/*.yml: role → codes[]`), UI выдачи
   прав; каталог кодов менять не придётся.

> **Статус:** механизм ролей реализован раньше запланированного (см.
> `05-mvp-scope.md`, дорожная карта): роли хранятся в `roles/<name>.yml`
> (файл переопределяет системный набор, удаление = сброс), поле `scope`
> определяет область курсовых прав; проверки — через `can()`/`canOnCourse()`
> (`server/utils/can.ts`). Редактор ролей — страница `/admin/roles` (админ).

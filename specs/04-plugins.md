# Плагинная система

## Ключевая идея

**Плагин = тип материала.** Ядро ничего не знает о конкретных типах контента.
Курс содержит не «конспекты», а материалы; каждый материал имеет `type`
в `material.yml`, и обработка содержимого делегируется плагину этого типа.

```
courses/<slug>/materials/
  pifagor/
    material.yml        # type: doc
    content/            # содержимое — целиком владение плагина doc
  vstupnyj-test/
    material.yml        # type: quiz
    content/            # quiz-плагин хранит как хочет (questions.yml, ...)
  opros-geometriya/
    material.yml        # type: survey
    content/
```

Ядро умеет ровно три вещи с материалом: **создать** (вызвав плагин),
**показать** (делегировав плагину), **удалить**.

## Контракт плагина

Плагин — TS-модуль в проекте, экспортирующий манифест:

```ts
// src/plugins/quiz/index.ts
definePlugin({
  type: 'quiz',
  title: 'Тест',
  server: {
    routes,   // API-роуты, монтируются под /api/materials/:course/:material/*
    hooks,    // подписки на события ядра
  },
  ui: {
    studentView: QuizStudentView,   // Vue-компонент для ученика
    teacherView: QuizTeacherView,   // для учителя
    preview: QuizPreview,
  },
})
```

- Роуты плагина монтируются в Nitro автоматически.
- На фронте — динамический Vue-компонент по `type` через реестр компонентов.
- Типобезопасность: реестр типов — статический объект, компилируемый вместе с приложением.

## Сознательные решения

1. **Compile-time плагины** (модули в коде), а не рантайм-загрузка с диска:
   рантайм-плагины — дыры в типизации, безопасности, санбоксы; для 2–10
   учителей неоправданно. При этом **данные** плагинов (type в material.yml,
   содержимое content/) — на диске, по тем же файловым правилам, и попадают
   в git-журнал бесплатно.
2. **Плагины — только типы материалов** (в первой версии контракта). Расширение
   контракта на «вертикальные фичи» (посещаемость, видеоконференции: свои
   топ-уровневые роуты и разделы навигации) — возможный шаг 2, тот же механизм,
   более широкий контракт.
3. **Первый плагин `doc` — уже в MVP**: md-страница с оглавлением, картинками,
   internal-ссылками между материалами (`[[slug]]`). Это проверка архитектуры
   на простейшем случае; `quiz` станет вторым и проверит контракт на
   несовпадении формы (у теста нет «текста», есть «вопросы и ответы»).

   > **Статус: реализован** (`server/material-plugins/doc.ts`, реестр
   > `server/ports/material-plugin.ts`). Отступление от схемы выше: у плагина
   > нет собственных `server.routes`/`ui`-манифеста — API материалов единый
   > (`/api/courses/:slug/materials/...`), а UI-страница материала общая;
   > специфика типа живёт в `io`/`render`. Этого достаточно, пока все типы —
   > «одна страница контента»; quiz потребует расширения контракта.

## Инфраструктура расширения (закладывается с первого дня)

1. **Реестр типов материалов** + контракт плагина (см. выше).
2. **Шина событий** (server-side, in-process):
   `material.created`, `material.updated`, `submission.created`,
   `submission.returned`, `assignment.published`, `deadline.passed`, ...
   Точечные хуки файлового адаптера (`mutation`) — отдельный, низкоуровневый
   канал для git-журнала.
3. **Контракт «материал → вклад в ДЗ»**: ДЗ в ядре остаётся всегда (текст + файлы),
   но может дополнительно ссылаться на материал любого типа. Тест как один из
   способов ответа — шаг 2, без изменения модели ДЗ.
